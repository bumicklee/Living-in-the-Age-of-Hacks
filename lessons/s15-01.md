# 15-1 캡스톤 ①: 다온마켓 연쇄 사고, 탐지
⏱ 약 12분 · 고칠 코드 없음(수강생 결과물은 `docs/incident/capstone/timeline.md`) · 랩 도구 `make capstone`·`python -m daon timeline`·Mailpit·Grafana · 아키텍처 A11 전체 · 15장 시작 모습: 관리자의 받는 사람 정보 수정도 감사 로그에 남는다(`change.order.receiver`)

**가상 시나리오입니다.** 모든 취약점을 막은 지 일주일 뒤, 새벽에 경보 메일이 한 통 옵니다. 점수판은 0인데 사고가 납니다. 다 막아도 **정상 권한을 훔치면** 들어옵니다. 그때 남는 것은 탐지입니다.

> 안전 원칙: `make capstone`은 새 공격 코드가 아닙니다. 앞 장의 재연이 이미 보내던 요청(T20 대량 조회, T34 환불, T35 권한)을 순서대로 묶었습니다. 127.0.0.1의 랩, 가짜 직원 `staff_night`, 가짜 값, 요청 수 고정. 모든 요청에 `X-Trace-Id: cap-<단계>-<순번>`.

## 따라 하기
1. **깨끗한 상태에서 시작합니다**(사고 전이라 지금은 wipe 해도 됩니다).
   ```bash
   make goto L=15-1
   make wipe && make up STACK=spring
   make capstone PART=1          # 가상 사고 재생(몇 분). 화면에는 단계 이름만 나옵니다
   ```
2. **경보 메일 한 통에서 출발합니다.** Mailpit(http://127.0.0.1:8025)의 `[다온 경보] data.read.bulk`. 메일의 `actor`를 적습니다.
3. **actor → 처음 들어온 순간.**
   ```bash
   python -m daon timeline --actor admin:staff_night --since 2h --audit --logins --incident capstone
   ```
   - 로그인 기록(`--logins`): 평소(가짜 사무실 IP, 저녁 9시대)와 다른 IP·시각. SECURITY 줄은 없습니다. 맞는 비밀번호의 로그인은 막지 않기 때문입니다.
   - 그보다 앞선 도구 이벤트 `secret.found.repository`(CI 시크릿 스캔, 6-2 규칙): 로컬 Gitea `daon/ops-scripts`의 설정 파일에 평문 비밀번호. 「비밀번호가 언제부터 밖에 있었나」가 나옵니다. `python -m daon gitea scan`
4. **감사 로그로 범위를 셉니다(8-3).** `order.list`의 `count` 합(돌려준 건수), 화면 마스킹(5-4) 덕분에 노출은 「주문 번호·상품·가린 연락처」입니다. Grafana에서는 `{stream="audit"} | json | actor="admin:staff_night"`.
5. **바뀐 것을 찾습니다.** 감사 로그 `change.order.receiver`의 `target`(주문 ID). 이 목록이 15-2 골라 복구의 입력입니다. 사고 뒤 **다른 사람**이 다시 바꾼 주문이 하나 있는지도 봅니다.
6. **trace_id 하나로 깊이 봅니다.** `python -m daon timeline --trace cap-5-001` → 관리자 앱 → 승인 서비스 줄. 승인 서비스가 거부했고 결제사 스텁에는 아무것도 가지 않았습니다.
7. **표로 정리합니다.** 양식 `docs/templates/캡스톤-타임라인.md`를 `docs/incident/capstone/timeline.md`로 복사해 「핵심 칸」과 「막힘 · 탐지만 · 놓침」 표를 채웁니다.
   ```bash
   make check L=15-1             # 핵심 칸을 정답 표와 비교(정상 시험 셋: 재생 결과·감사 로그·경보 메일)
   ```
   정답 표는 수업 끝에: `make capstone PART=answer`.

## 막힐 때
- 경보가 오지 않는다: A5(Loki·Grafana)와 Mailpit이 떠 있는지, 8-4 규칙이 올라갔는지(`make alert-rules`). 경보는 30초마다 평가합니다.
- 타임라인에 줄이 너무 많다: 재생 전에 `make wipe`. 시각 구간(`--since`)을 좁힙니다.
- 「배송지 변경은 왜 SECURITY 이벤트가 없나」: 정상 권한의 정상 기능이라 막을 지점이 없었습니다. 그래서 감사 로그와 경보 규칙이 필요합니다(15-2에서 규칙을 더합니다).
- `make wipe`가 멈춘다: 사고 기록 폴더(`.daon/incident/capstone/`)가 생겼습니다. 사고 중에는 wipe 금지입니다(14-4). 15-2까지 그대로 둡니다.

## 확인 문제
1. 「막힌」 단계 두 개와 「탐지만 된」 단계 두 개는? (막힘: 남은 금액 초과 환불, 권한 상승 없는 고위험 기능. 탐지만: 새 IP 로그인, 대량 조회.)
2. 노출 범위를 「회원 N명」이 아니라 「주문 N건, 가린 연락처」로 말할 수 있었던 이유는? (감사 로그가 대상 ID와 건수를 남기고, 화면 마스킹으로 원문이 응답에 없었다.)
3. 시크릿 유출 시각을 무엇으로 알았나? (CI 시크릿 스캔 경고 시각과 커밋 시각.)
