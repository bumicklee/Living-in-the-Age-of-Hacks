# 10-2 DB로 막기: 조건부 UPDATE·잠금·유니크 제약
⏱ 약 11분 · 고칠 파일 자바 2개 + 새 파일 3개(DAO·매퍼 XML·제약) · 아키텍처 변화 없음 · 방어 스위치 `money-race`

## 따라 하기
1. **레드부터 봅니다.**
   ```bash
   make goto L=10-2
   make money-reset
   make replay T=25            # 10-1과 같은 표 [레드]
   make check L=10-2           # 7개 중 5개 레드(정상 2개는 그린)
   ```
2. **조건부 UPDATE(새 ✏️ `mall-portal/.../dao/DaonMoneyDao.java`·`resources/dao/DaonMoneyDao.xml`).** 검사를 `WHERE`에 넣고 영향받은 행 수로 성공을 판단합니다. 값은 모두 `#{}`.
   - 쿠폰 수량: `UPDATE sms_coupon SET count = count - 1, receive_count = receive_count + 1 WHERE id = #{couponId} AND count > 0`
   - 포인트: `UPDATE ums_member SET integration = integration - #{use} WHERE id = #{memberId} AND integration >= #{use}`
   - 취소 환원: `integration = integration + #{amount}`(읽고-더하고-쓰기 대신)
   - 재고 잠금: `lock_stock = lock_stock + #{qty} WHERE id = #{skuId} AND stock - lock_stock >= #{qty}`(원본도 읽고-더해-쓰기였습니다)
3. **쿠폰 받기(✏️ `UmsMemberCouponServiceImpl.add()`).** 순서는 ① 이력 INSERT(유니크 제약) → ② 수량 조건부 UPDATE → 둘 다 성공해야 커밋. 중복 키 예외(`DuplicateKeyException`)는 「이미 받은 쿠폰」, ②가 0행이면 「모두 소진」으로 바꿉니다. 앞의 건수 확인은 정상 사용자에게 빨리 알려 주는 용도일 뿐, 막는 것은 DB입니다.
4. **1인 한도는 DB 제약(새 ✏️ `config/DaonMoneySchema.java`).** 앱이 뜰 때 한 번 `ALTER TABLE sms_coupon_history ADD UNIQUE KEY uk_daon_coupon_member (coupon_id, member_id)`. 이미 겹친 행이 있으면 걸 수 없으니 경고만 남깁니다(`make wipe` 뒤 다시). 시드 쿠폰은 모두 1인 1장입니다. 1인 3장 쿠폰은 이 제약으로 못 막습니다: 회원·쿠폰별 카운터 행을 `WHERE used < 3`으로 조건부 UPDATE(그림).
5. **포인트(✏️ `OmsPortalOrderServiceImpl`).** `generateOrder()`의 차감을 조건부 UPDATE로 바꾸고 0행이면 `Asserts.fail` → 주문 전체가 되돌아갑니다(`@Transactional`). 캐시된 회원 객체의 포인트로 계산하지 않고, 바꾼 뒤 회원 캐시를 지웁니다. 쓴 포인트(`use_integration`)는 주문 행을 저장하기 **전에** 넣습니다(원본은 저장 뒤라 DB에 남지 않아 취소 때 돌려줄 수 없었습니다).
6. **잠금은 그림으로.** `SELECT … FOR UPDATE`는 읽은 값으로 복잡한 계산을 해야 할 때만. Redis 잠금은 만료·장애·DB 밖이라는 세 함정이 있습니다. 잠금이 풀려도 DB 조건이 마지막 방어선입니다.
7. **확인합니다.**
   ```bash
   make up STACK=spring          # 제약은 앱이 뜰 때 걸린다
   make replay T=25              # 성공 1·거절 99, 주문 1개·남은 포인트 0 [그린]
   make check L=10-2             # 7개(정상 2개 포함)
   make logs S=mall-portal | grep coupon.denied.limit_reached | wc -l   # 99줄 가까이, count가 커진다
   ```
8. **스위치.** `make switch K=money-race V=off`(앱이 다시 뜰 때 유니크 제약도 지움) → `make replay T=25` 레드 → `V=on`.

## 막힐 때
- 앱 로그에 「유니크 제약을 걸 수 없습니다」: 10-1 재연이 남긴 중복 행입니다. `make money-reset`(또는 `make wipe`) 뒤 `make up`.
- 「DB 권한」 경고: 앱 DB 계정(6-3 동적 계정)은 `sms_coupon_history`의 ALTER·INDEX만 더 받습니다(`infra/openbao/init.sh`). 6-3 이후 랩을 다시 띄우지 않았다면 `make up`.
- 영향받은 행 수를 안 보면 조건부 UPDATE도 소용없습니다. 매퍼의 반환값(int)을 꼭 봅니다.
- 99개가 거절되며 로그가 많이 쌓입니다. 로그를 줄이려고 이벤트를 빼지 않습니다. `count`가 그 신호입니다.
- Express: `diffs/s10-02/express.diff`는 EverShop의 쿠폰 사용 횟수 트리거(`set_coupon_used_time`)를 조건부 UPDATE + 0행이면 주문 거절로 바꾸는 마이그레이션 하나입니다(검사는 `timeUsedValidator`, 갱신은 주문 INSERT 뒤 트리거라 같은 틈이 있습니다).

## 남는 이벤트
`coupon.denied.limit_reached`(WARN, actor `member:<ID>`, target `coupon:<ID>`, reason 「1인 한도(유니크 제약)」·「수량 소진(조건부 갱신 0행)」), `points.denied.insufficient`(WARN, actor·target `member:<ID>`).
