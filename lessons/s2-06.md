# 2-6 DNS 리바인딩: 허용한 이름이 내부를 가리킨다
⏱ 약 9분 · 고칠 파일 1개 · 바뀌는 줄 약 30줄

다온마켓 운영팀은 장애 때 설정 값을 보려고 「다온 운영 도구」를 만들었습니다([교육용 추가]). 관리자 앱 안에서 8095 포트로만 열리고, 내 PC(127.0.0.1)에만 공개합니다. 「내 PC에서만 열리니 괜찮다」고 보고 로그인도 없습니다.

DNS 리바인딩은 이 생각을 무너뜨립니다.
1. 운영자가 PC 브라우저로 공격자 사이트 `rebind.attacker.example`을 엽니다. 처음에는 공격자 서버의 주소가 돌아옵니다.
2. 페이지의 스크립트가 잠시 기다린 뒤 같은 이름으로 `:8095/ops/config`를 부릅니다. 이번에는 DNS가 `127.0.0.1`을 돌려줍니다.
3. 브라우저는 이름이 같으니 같은 출처로 보고 응답을 스크립트에 넘깁니다. 운영 도구의 설정 값이 공격자 페이지로 넘어갑니다.

이때 운영 도구에 도착하는 요청은 하나뿐이고, 그 요청의 Host 헤더에는 공격자 이름(`rebind.attacker.example:8095`)이 실려 있습니다. 재연은 브라우저와 DNS 없이 바로 그 요청을 만듭니다.

## 따라 하기
1. **레드인 것부터 봅니다.**
   ```bash
   make goto L=2-6
   make replay T=05
   make check L=2-6
   ```
   `Host: rebind.attacker.example:8095`를 달고 `127.0.0.1:8095/ops/config`를 부르면 설정 값이 그대로 나옵니다.
2. **Host 허용 목록을 둡니다.** `spring/mall-admin/.../daon/DaonOpsGuardFilter.java`의 ✏️ 2-6 표시.
   ```java
   @Value("${daon.ops.hosts:127.0.0.1:8095,localhost:8095}")
   private String allowedHostsConfig;
   ...
   if (onOpsPort) {
       String host = request.getHeader("Host");
       if (host == null || !allowedHosts().contains(host.trim().toLowerCase(Locale.ROOT))) {
           response.setStatus(HttpServletResponse.SC_FORBIDDEN);
           response.setContentType("application/json;charset=UTF-8");
           response.getWriter().write("{\"code\":403,\"message\":\"허용하지 않은 Host입니다\"}");
           return;
       }
   }
   ```
   - 이 도구를 부를 때 쓰는 이름(`127.0.0.1:8095`, `localhost:8095`)만 허용합니다. compose가 `DAON_OPS_HOSTS`로 넣어 줍니다(`infra/.env`에서 포트를 바꾸면 같이 바뀝니다).
   - 이 필터는 Spring Security보다 먼저 돕니다(`DaonOpsConfig`가 가장 앞 순서로 등록).
3. **⑤ 탐지: 낯선 Host를 남깁니다.** 403을 쓰기 전에 보안 이벤트를 남깁니다.
   ```java
   SecurityEventLogger.denied("request.denied.host", "2-6")
           .actor("anonymous")
           .target("host:" + (host == null ? "-" : host.length() > 64 ? host.substring(0, 64) : host))
           .reason("허용하지 않은 Host")
           .request(request)
           .log();
   ```
   - 필터는 요청 문맥이 만들어지기 전에 돌기 때문에 `.request(request)`로 요청을 직접 넘깁니다.
   - 운영 도구에 낯선 Host가 왔다는 것은 누군가의 브라우저가 공격 페이지를 열었다는 뜻입니다. 한 번이라도 경보 후보입니다.
4. **확인합니다.**
   ```bash
   make check L=2-6
   make replay T=05      # [그린] 막힘
   make logs S=mall-admin | grep request.denied.host
   ```
   이 PC에서 `127.0.0.1`·`localhost`로 부르는 정상 요청은 그대로 200이어야 합니다.

## 남는 일
- Host 허용 목록은 DNS 리바인딩을 막지만, 서버 안에서 `127.0.0.1:8095`로 부르는 SSRF(2-5)는 막지 못합니다. Host가 허용한 이름 그대로이기 때문입니다. 그래서 2-5의 막기가 따로 있어야 합니다.
- 로컬 도구에도 인증을 둡니다. 토큰 하나라도 있으면 리바인딩된 브라우저는 그 값을 모르니 설정 값을 읽지 못합니다.
- 해석 결과 고정(DNS pinning)은 브라우저·프록시 쪽 방어입니다. 서버는 Host 확인을 먼저 합니다.

## Express라면
`diffs/s2-06/express.diff`. EverShop은 개발 PC의 `localhost:3000`에서 관리자 세션 쿠키로 돕니다. 쿠키 인증은 리바인딩된 브라우저가 그대로 실어 보내므로, 같은 Host 허용 목록을 앱 맨 앞 미들웨어로 둡니다.

## 선택: 끄면 레드, 켜면 그린(영상용 방어 스위치)
완료 지점(`make goto L=2-6 AT=done`, 또는 그 뒤 수업)의 정답 코드는 `secure-kit.host-allowlist.enabled` 스위치를 읽습니다. 코드를 고치지 않고 보호를 껐다 켤 수 있습니다. 시작 지점 코드는 스위치를 읽지 않으니, 손으로 고치는 실습은 그대로입니다.
```bash
make switch K=host-allowlist V=off    # mall-admin만 다시 띄웁니다(30초쯤)
make replay T=05               # 낯선 Host로 운영 도구 설정이 다시 보이고(레드)
make switch K=host-allowlist V=on
make replay T=05               # 다시 막힙니다(그린)
```
지금 값은 `make switch`(목록)나 `make lab`(랩 상황판 http://127.0.0.1:8099/lab)에서 봅니다. 끈 채로 두면 `make check`가 알림을 띄웁니다.
