# 10-1 쿠폰 한 장으로 열 번 할인
⏱ 약 9분 · 원리 수업(고치기 없음, `make check` 없음) · 아키텍처 변화 없음 · 재연 T25

## 따라 하기
1. **시작 지점으로 갑니다.**
   ```bash
   make goto L=10-1
   make up STACK=spring
   make money-reset          # alice·bob 포인트·쿠폰 이력을 되돌린다(앞에서 재연했다면)
   ```
2. **코드를 봅니다(`mall-portal/.../service/impl/UmsMemberCouponServiceImpl.java`의 `add()`).** 쿠폰을 읽고 → 수량이 남았는지·이미 받았는지 세고(`if`) → 이력을 저장하고 → `count - 1`을 덮어씁니다. 「조회 → if → 저장」 모양입니다. 포인트도 같습니다: `OmsPortalOrderServiceImpl.generateOrder()`는 로그인할 때 읽어 둔 회원 객체의 포인트에서 쓴 만큼 빼서 덮어씁니다.
3. **재연합니다.**
   ```bash
   make replay T=25
   ```
   - 장면 1: alice 토큰으로 쿠폰 101(「다온 첫 주문 3천원 할인」, 1인 한도 1장)의 받기 요청을 **100개 한 번에** 보냅니다. 표의 「성공 응답 · 저장된 행 · 줄어든 수량」을 봅니다. 2 이상이면 뚫린 것입니다.
   - 장면 2: alice 포인트를 1,000점으로 맞추고, 1,000점을 쓰는 주문 요청 10개를 한 번에 보냅니다. 주문이 둘 이상이면 뚫린 것입니다(만든 주문은 재연이 닫습니다).
   - 노트북에서는 100개가 정확히 같은 순간에 가지 않아 결과가 매번 다를 수 있습니다. 재연은 요청을 먼저 준비해 두고 한꺼번에 출발시킵니다(한 번에 최대 100개, 반복 없음).
4. **SQL로 다시 셉니다.**
   ```bash
   docker exec daon-mysql-1 mysql -uroot -proot mall -e "SELECT COUNT(*) FROM sms_coupon_history WHERE coupon_id=101 AND member_id=101; SELECT count, receive_count FROM sms_coupon WHERE id=101;"
   ```
   「성공 응답 수 = 저장된 행 수」인지, 「줄어든 수량 = 저장된 행 수」인지 맞춰 봅니다. 줄어든 수량이 더 적으면 `count - 1`을 서로 덮어쓴 것(잃어버린 갱신)입니다.
5. **탐지 신호를 찾아봅니다.** 막기 전에는 보안 이벤트가 없습니다. 같은 회원·같은 쿠폰의 받기 요청이 1초 안에 몰린 줄을 봅니다.
   ```bash
   make logs S=mall-portal | grep "/member/coupon/add" | tail -20
   ```

## 막힐 때
- 첫 요청부터 「이미 받은 쿠폰입니다」: 앞 재연이 남긴 이력입니다. `make money-reset`.
- 레드가 안 나온다(성공 1): PC가 요청을 차례로 처리했을 수 있습니다. 한 번 더 돌려 봅니다. 10-2를 마친 DB(유니크 제약)라면 앱이 다시 뜰 때 시작 지점 코드가 제약을 지웁니다(`make up`).
- `@Transactional`이 있는데 왜? 기본 격리 수준에서 두 트랜잭션이 같은 「0장」을 읽고 둘 다 통과합니다. 트랜잭션은 「한 번에 하나」를 보장하지 않습니다.
