# 14-4 첫 한 시간 런북: 격리·증거·연락
⏱ 약 11분 · 고칠 파일 자바 3곳(mall-security `TokenService`·`JwtAuthenticationTokenFilter`, 고객 앱 `UmsMemberServiceImpl.login()`) + 새 파일 1개(`DaonIncidentController`) + 설정 2개(`OpsElevationGate`·`MallSecurityConfig`) · 랩 도구 `make drill D=14-4`·`python -m daon timeline`·`make evidence` · 아키텍처 변화 없음(A11 잠금 버킷을 증거 보관에 씀) · 방어 스위치 없음(사고 대응 도구)

경보 메일 한 통에서 출발합니다. 이 수업은 **새 로그를 만들지 않습니다.** 2장부터 막은 자리마다 심어 둔 SECURITY 줄과 `trace_id`로 「무엇이 시도됐고, 어디까지 갔나」를 다시 세웁니다. 그리고 첫 한 시간에 할 일(지휘자·인지 시각 → 증거 → 격리 → 타임라인 → 연락)을 순서대로 해 봅니다.

> 안전 원칙: 모의 침해는 앞 장들에서 이미 막아 둔 요청만, 가짜 고객 셋(daon117·118·119)으로, 127.0.0.1의 랩에만 보냅니다. 요청 수는 고정입니다. 모든 요청에 `X-Trace-Id: drill-14-4-<순번>`이 붙습니다.

## 따라 하기
1. **런북 첫 장을 옆에 띄웁니다.** `docs/runbooks/01-first-hour.md`. 첫 줄은 「사고 중에는 `make wipe`·`make down -v` 금지」입니다(증거를 모으지 않은 사고 기록이 있으면 `make wipe`가 멈춥니다).
2. **모의 침해를 재생합니다.**
   ```bash
   make goto L=14-4
   make up STACK=spring
   make drill D=14-4             # 요청 약 30개, 1분 남짓. 추적 번호 drill-14-4-0001 ~
   make check L=14-4
   ```
3. **타임라인(이 수업의 중심).** 경보 메일의 `actor`에서 출발합니다.
   ```bash
   python -m daon timeline --actor member:117 --since 10m --trace-prefix drill-14-4- --incident INC-14-4
   python -m daon timeline --trace drill-14-4-0008      # 한 요청이 지나간 줄(게이트웨이·앱 일반 로그 [번호]·SECURITY)
   make audit-verify                                    # 8-6 해시 체인: 이 타임라인을 보고서에 써도 되나
   ```
   1단계 actor → 2단계 같은 ip로 넓히기(계정 셋이 나옴, 판단 칸에는 「추정」) → 3단계 trace_id → 4단계 감사 로그(같은 시간대 정상 권한 조회) → 5단계 영향 범위(ID로만: 시도당한 주문 12건·열린 주문 0건) → 6단계 로그를 믿을 수 있나. 결과물 `.daon/incident/INC-14-4/timeline.md`. Grafana에서는 `{stream="security"} | json | actor="member:117"`.
4. **증거부터(공격이 끝났으면), 격리부터(진행 중이고 돈·데이터가 나가고 있으면).**
   ```bash
   make evidence INCIDENT=INC-14-4   # 로그·감사 로그 사본·DB 스냅샷·이미지 다이제스트 → evidence.sha256 → 잠금 버킷 incident/INC-14-4/
   ```
5. **격리(✏️ 새 파일 `DaonIncidentController`, `POST /daon/incident/lock-actor`).** 사유·사고 번호 필수, 고위험(✏️ `OpsElevationGate` 묶음 `incident-response`, ✏️ `MallSecurityConfig`).
   - ① 회원 상태 0 → ✏️ 고객 앱 `login()`이 비밀번호가 맞아도 같은 문구로 거부(`auth.denied.disabled_account`, 14-4)
   - ② 고객 앱 회원 캐시(`mall:ums:member:<아이디>`) 지우기 → 지금 쓰는 토큰도 다음 요청부터 401
   - ③ 토큰 일괄 폐기(✏️ `TokenService.revokeAllOf()`·`cutOff()`, ✏️ 필터): 계정마다 끊은 시각을 두고, 그 전에 로그인해 받은 액세스 토큰·갱신 토큰을 모두 받지 않습니다. 잠금을 풀어도 그 전 토큰은 살아나지 않습니다
   - ④ `incident.actor.locked`(INFO)·감사 로그 `incident.lock-actor`. 대응 행동도 타임라인의 한 줄입니다
6. **확인합니다.**
   ```bash
   make up STACK=spring
   make check L=14-4             # 6개(정상 4개: 다른 고객·타임라인 정답 표·증거·해시 체인)
   make drill D=14-4             # 117을 잠근 뒤 다시 돌리면 1)부터 거부(재생은 처음에 랩 도구로 잠금을 풉니다)
   ```
7. **연락(마지막 30초).** 런북의 연락표: 사고 지휘자·개발 책임자·개인정보 보호책임자·법무·경영진·고객 센터. 누가 누구에게, 몇 분 안에, 무엇을(사실·추정·모름을 나눠서).

## 막힐 때
- 증거가 사라졌다: `make wipe`·`make down -v`를 먼저 했습니다. 런북 첫 줄을 지킵니다.
- 타임라인에 줄이 너무 많다: actor와 시각 구간(`--since`), 모의 침해 번호(`--trace-prefix`)로 먼저 좁힙니다.
- 게이트웨이 줄에 번호가 없다: 고객 앱을 8085로 바로 불렀습니다(게이트웨이를 거치지 않음). 8086(A7) 입구로 부르면 게이트웨이 접근 로그에도 같은 번호가 남습니다.
- 시각이 서버마다 다르다: 모든 줄은 `+09:00`이고 도구는 UTC로 바꿔 비교합니다. 컨테이너 `TZ`를 봅니다.
- 「IP 차단은?」: IP는 쉽게 바뀌므로 계정 잠금이 먼저입니다(입구 차단은 이 랩에 넣지 않았습니다).
- Express: `diffs/s14-04/express.diff`는 EverShop 고객 상태를 잠그고 그 고객의 세션을 지우는 관리자 API를 더합니다.

## 확인 문제
1. 경보에서 출발해 「한 사람이 계정 셋을 썼다」를 알아낸 단서는? (첫 계정의 SECURITY 줄에 있는 `ip`로 다시 찾았을 때 같은 IP의 다른 actor가 나왔다. 단정하지 않고 「추정」으로 적는다.)
2. trace_id 하나로 무엇을 확인하나? (그 요청이 게이트웨이부터 앱·큐·승인 서비스까지 어디를 지났고 어디서 막혔는지.)
3. 증거 파일에 sha256 목록을 붙이고 잠금 버킷에 두는 이유는? (나중에 증거가 바뀌지 않았음을 보이기 위해서. 잠금 버킷은 사고 대응자도 지울 수 없다.)
4. 영향 범위를 개인정보 원문 없이 셀 수 있는 이유는? (공격 징후 로그의 `target`에 ID만 남기도록 강의 내내 규칙을 지켰기 때문이다.)
