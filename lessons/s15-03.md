# 15-3 최종 점수판: 취약 37개 → 0개
⏱ 약 9분 · 고칠 파일 1개(✏️ `course/audit.yaml`: 점검표 74행의 처리 결과·근거) · 랩 도구 `make final-score`·`make audit`·`make verify-course`

강의 첫 섹션에서 우리는 고치기 전에 먼저 점검했습니다. 같은 재연, 같은 점검 방법으로 처음과 끝을 비교합니다. 숫자 둘의 역할은 1-1과 같습니다: **재연되는 취약 37개(점수판)**와 **처음 점검에서 찾은 개선 항목 74개(점검표)**.

## 따라 하기
1. **시작 상태와 최종 상태를 같은 재연으로.**
   ```bash
   make final-score              # 1-12 시작 지점(점수판 37) → 15-3 완료 지점(0). 앱을 두 번 다시 빌드합니다(수십 분)
   make lab                      # /lab 점수판
   ```
2. **점검표 74행을 다시 돌립니다.** 행마다 「다시 확인하는 방법」이 하나씩 있습니다: 재연(T 번호) · 수업 시험 · 설정 파일 · 의존성(오늘 날짜로 다시 조회) · Express diff · 문서.
   ```bash
   make audit                    # 결과 표: ID · 처음 심각도 · 처리 결과 · 다시 확인 · 근거 · 남은 위험
   make audit ONLINE=1           # 의존성 행(OSV·npm audit)을 오늘 날짜로. 인터넷이 필요합니다(오프라인이면 「조회 안 함」)
   ```
3. **✏️ `course/audit.yaml`의 「처리 결과」를 채웁니다.** 네 가지뿐입니다.
   - **고침**: 코드·설정을 바꾸고 시험이 그린
   - **완화**: 구조로 피해를 줄임(예: DB TLS는 망 분리 A1과 함께 판단)
   - **수용**: 고치지 않기로 하고 이유와 다시 볼 날을 적음
   - **확인 필요**: 아직 판단 근거가 없음(예: 새로 나온 의존성 권고)
4. **확인합니다.**
   ```bash
   make check L=15-3             # 74행 처리 결과·근거 · 「고침」 행이 그린 · 지금 점수판 0/37
   make verify-course            # 모든 수업 「시작 레드 → 완료 그린」(오래 걸립니다)
   ```
   결과는 `reports/final-check/`에 날짜와 커밋으로 남습니다. 최종 점검 보고서는 최초 점검 보고서와 같은 형식에 「처리 결과」·「근거」 칸만 더한 것입니다. 다음 수업에서 자기 서비스에 쓸 양식이 이것입니다.
5. **정직하게 말할 것.** 점수판은 0입니다. 하지만 점검표 전체가 「고침」은 아닙니다. 의존성 권고는 시간이 지나면 새로 생깁니다. 점수판은 「강의가 약속한 재연 37개를 막았다」, 보고서는 「74개 각각의 처리 결과와 남은 위험을 안다」입니다.

## 막힐 때
- 시작 지점 점수가 37이 아니다: Express E항목은 점수판에 섞지 않습니다(점검표로 셉니다). `scoreboard/spring.json`의 `total`이 37인지.
- `make audit`의 의존성 행이 「조회 안 함」: 오프라인입니다. `ONLINE=1`로 한 번만 조회합니다.
- `make verify-course`가 오래 걸린다: `make verify-course ONLY=15-3`처럼 수업 하나씩.

## 확인 문제
1. 처리 결과 네 가지는? (고침, 완화, 수용, 확인 필요.)
2. 점수판이 0인데 보고서에 「확인 필요」가 남을 수 있는 이유는? (점수판은 강의가 정한 재연만 보고, 의존성 권고처럼 시간이 지나며 새로 생기는 위험은 점수판 밖에 있다.)
3. F23(설정 파일의 자격증명)을 다시 확인하는 방법 두 가지는? (보강한 시크릿 스캔 규칙을 다시 돌리기, 기본값이면 기동을 거부하는 시험이 그린인지 보기.)
