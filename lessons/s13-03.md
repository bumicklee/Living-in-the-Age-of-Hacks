# 13-3 승인 정책 엔진: 서명하는 쪽이 내용을 읽는다
⏱ 약 12분 · 고칠 파일 자바 3곳(관리자 앱 `OmsOrderReturnApplyServiceImpl.updateStatus()`·`DaonRefundExecutor`, 승인 서비스 `ApprovalPolicy.evaluate()`) + 새 파일 3개(`DaonApprovalClient`·`DaonApprovalToken`·`DaonRefundController`) + 설정 2개(`infra/arch.txt`·`MallSecurityConfig`) · 아키텍처 **A10** · 방어 스위치 `approval`

관리자 앱은 「요청」만 합니다. **판단은 원장(DB)을 직접 읽는 승인 서비스가**, **실행은 승인 서비스가 서명한 토큰을 확인한 실행기가** 합니다. 관리자 앱 혼자서는 승인을 만들 수 없습니다.

> 안전 원칙: 직원·주문·금액은 모두 가짜이고, 환불은 가짜 결제사(payment-stub)에 기록만 남습니다. 서명 키는 랩을 띄울 때 금고(OpenBao) 안에서 만들어지고 저장소에는 없습니다. 「위조·금액 변경 토큰」은 실행기가 거절하는지만 보는 시험입니다.

## 따라 하기
1. **레드부터 봅니다.**
   ```bash
   make goto L=13-3
   make up STACK=spring
   make replay T=34 PART=remaining   # 결제 39,000원 주문에 3,000,000원 환불·처리자 admin [레드]
   open http://127.0.0.1:9101/_stub/refunds   # 가짜 결제사 환불 목록
   make check L=13-3
   ```
2. **A10 연결(✏️ `infra/arch.txt`에 `a10`).** `infra/compose.a10.yml`을 읽어 봅니다.
   - 승인 서비스 `approval`(127.0.0.1:8097, 작은 Spring Boot 앱, 소스 `infra/approval/`). 관리자 앱과 코드·DB 계정·금고 권한이 다릅니다.
   - DB 계정: 금고의 동적 계정(역할 `approval`). 주문·반품·관리자 표는 **읽기만**, `daon_approval_*` 두 표만 씁니다(6-3의 앱별 최소 권한).
   - 서명 키 `transit/keys/daon-approval`: **서명은 승인 서비스 정책에만**, 관리자 앱은 **확인(verify)만**(`approval-init`이 만듭니다).
3. **승인 서비스(✏️ `infra/approval/src/.../ApprovalPolicy.java`의 `evaluate()`).**
   - 남은 결제 금액 = `oms_order.pay_amount` − 이 서비스가 이미 잡아 둔 환불 합계. 요청 금액이 넘으면 거부 + `approval.denied.over_remaining`.
   - 정책 파일 `infra/approval/policy.yml`(가짜 기준): 1회 한도·같은 주문 하루 3번·고액 기준(13-4에서 씀). 위반이면 `approval.denied.policy_limit`.
   - 통과하면 승인 기록 `(반품, 금액, 요청자, 승인자, 1회용 번호, 만료)`과 같은 내용을 서명한 **승인 토큰**을 돌려줍니다. 요청자는 관리자 토큰을 승인 서비스가 직접 확인해 정합니다(본문의 이름을 받지 않습니다).
4. **관리자 앱(✏️ `OmsOrderReturnApplyServiceImpl.updateStatus()`).**
   - `handleMan`은 로그인 정보에서. 요청 본문의 값은 버립니다.
   - 대기(0) → 확인(1)은 조건부 UPDATE(`WHERE id = ? AND status = 0`). 두 번 눌러도 환불은 한 번입니다(10-4와 같은 원리).
   - `returnAmount`는 저장하지 않고 「요청 금액」으로만 `DaonApprovalClient.requestRefund()`에 넘깁니다. 거부되면 확인을 되돌립니다.
5. **실행기(✏️ `DaonRefundExecutor.execute(returnId, token)`).** ⓐ 서명(금고 transit verify) ⓑ 반품 ID·주문·상태가 DB와 같은지 ⓒ 만료 전 ⓓ 1회용 번호를 처음 쓰는지 → 모두 맞을 때만 **토큰 속 금액**으로 가짜 결제사를 부릅니다. 하나라도 틀리면 `refund.denied.no_approval`. 입구 `POST /daon/refund/execute`는 반품 관리 권한(✏️ `MallSecurityConfig`).
6. **확인합니다.**
   ```bash
   make up STACK=spring
   make replay T=34 PART=remaining   # 승인 서비스가 거부: 남은 결제 금액 초과 · 환불 0건 · 처리자 staff_order [그린]
   make check L=13-3                 # 9개(정상 1개: 10,000원 환불은 바로 1건)
   make approval-status
   make logs S=approval | grep SECURITY
   make logs S=mall-admin | grep refund.denied
   make mem                          # 승인 서비스 +256MB 근처인지
   ```
7. **같은 trace_id를 봅니다.** `approval.denied.over_remaining` 줄의 `trace_id`가 관리자 앱이 받은 요청의 `X-Trace-Id`와 같습니다(관리자 앱이 승인 서비스 요청 헤더로 넘김). 14-4 타임라인에서 이 연결을 씁니다. A5 이후라 Grafana에서 `{app="approval", stream="security"}`로도 봅니다.
8. **스위치.** `make switch K=approval V=off` → `make replay T=34 PART=remaining` 레드 → `V=on`.

## 막힐 때
- 승인 서비스가 DB에 못 붙는다: `make logs S=approval-init`(DB 역할·정책을 만들었는지), `make logs S=approval`(「전용 DB 계정을 받았습니다」 줄).
- 정상 환불이 `refund.denied.no_approval`로 막힌다: 토큰 금액은 원 단위 정수 글자(`"10000"`)입니다. 만료(5분)는 관리자 앱 시계(랩 시계 A13)로 봅니다. 시험이 시계를 밀어 둔 채 끝났으면 `make approval-reset`.
- 「관리자 앱이 통째로 뚫리면 실행기의 확인을 건너뛸 수 있지 않나」: 그렇습니다. 승인 토큰은 「앱 혼자 승인을 만들 수 없게」 하는 것이고, 건너뛴 실행은 결제사 환불 목록과 승인 기록을 맞춰 보는 대사(10-5 방식)로 찾습니다.
- 「승인 서비스도 뚫리면 끝 아니냐」: 맞습니다. 그래서 13-4에서 사람 둘·다른 경로·지연을 더하고, 13-6에서 운영 접근을 줄입니다.
- trace_id가 승인 서비스 줄에 비어 있다: `DaonApprovalClient`가 `X-Trace-Id`를 넣는지 봅니다.
- Express: `diffs/s13-03/express.diff`는 EverShop 환불(`createOrderRefund`)이 `refundOrder()`를 바로 부르지 않고 승인 서비스에 요청한 뒤 승인 토큰을 확인하게 바꿉니다. EverShop 원본 `refundOrder()`는 이미 「남은 결제 금액 이하」를 확인합니다(좋은 예). 바뀌는 점은 「누가 실행하느냐」입니다.

## 남는 이벤트
