# 10-4 결제 콜백 멱등 처리와 단방향 상태 전이
⏱ 약 12분 · 고칠 파일 자바 1개 + 설정 1개 + 고객 웹 1개 + 새 파일 6개 · 아키텍처 변화 없음(가짜 결제사 `payment-stub` 127.0.0.1:9101) · 방어 스위치 `pay-webhook`

## 따라 하기
1. **레드부터 봅니다.**
   ```bash
   make goto L=10-4
   make replay T=26            # 장면 A: bob이 alice 주문을 결제 완료로 바꾼다 [레드]. 장면 B는 /pay/start가 없어 건너뜀
   make check L=10-4           # 7개 중 6개 레드
   ```
2. **입구 정리(✏️ `OmsPortalOrderController`, `application.yml`, `web/html/app.js`).**
   - `paySuccess`를 고객 API에서 뺍니다. 지운 자리에 얇은 거절 처리기(HTTP 410 + `payment.denied.client_call`)를 남깁니다. 정상 고객 웹은 더 이상 부르지 않으므로 부르면 신호입니다.
   - `/alipay/**`를 화이트리스트에서 지우고 `/pay/webhook` 하나만 엽니다. 랩은 알리페이를 쓰지 않습니다.
   - 고객 웹 「가짜 결제하기」는 새 `POST /pay/start`를 부릅니다(카드 토큰은 가짜 테스트 토큰 `tok_test_4242`).
3. **결제 시작(새 ✏️ `controller/DaonCheckoutController.java`).** 본인 주문이고 결제 대기(0)일 때만. 금액은 **서버가 주문에서 읽어** 가짜 결제사 `POST /v1/payments`에 보냅니다(요청에서 받지 않는다, 10-8과 같은 원칙). 결제 완료는 여기서 정하지 않습니다.
4. **웹훅 수신(새 ✏️ `controller/DaonPaymentWebhookController.java`·`component/DaonWebhookVerifier.java`·`service/impl/DaonPaymentService.java`).** 순서는 ① 서명 → ② 중복 → ③ 금액 → ④ 상태 전이.
   - ① `@RequestBody byte[]`로 **받은 바이트 그대로** HMAC-SHA256을 다시 계산하고 `MessageDigest.isEqual`로 비교합니다. 비밀값은 OpenBao KV `secret/daon/payment-webhook`(랩 값 `lab-fake-webhook-secret`). 틀리면 401.
   - ② `oms_payment_event(payment_id, event)` 유니크 표에 먼저 INSERT. 중복 키면 **200**을 주고 아무것도 하지 않습니다(4xx를 주면 결제사가 계속 다시 보냅니다).
   - ③ 웹훅 `amount`와 주문 `pay_amount`가 다르면 상태를 바꾸지 않고 422.
   - ④ `UPDATE oms_order SET status = 1, payment_time = NOW() WHERE order_sn = #{sn} AND status = 0`. 0행이면 역행·중복 전이(409). 재고 차감은 이 UPDATE가 1행일 때만.
   - 상태 전이표(0 → 1 → 2 → 3, 0 → 4)는 `DaonPaymentService.TRANSITIONS` 상수 하나로 둡니다. 표는 앱이 뜰 때 `DaonMoneySchema`가 만듭니다.
5. **확인합니다.**
   ```bash
   make up STACK=spring
   make replay T=26            # 장면 A 410·상태 그대로, 장면 B: 웹훅 두 번 모두 200, 결제 완료·재고 차감 한 번 [그린]
   curl -s 127.0.0.1:9101/v1/webhooks | tail -c 400
   make check L=10-4           # 7개(정상 1개 포함)
   ```
   고객 웹(127.0.0.1:8088)에서 alice로 주문하고 「가짜 결제하기」 → 1~2초 뒤 「배송 대기」로 바뀌는 것을 봅니다.
6. **스위치.** `make switch K=pay-webhook V=off` → 장면 A 레드(옛 paySuccess가 다시 통함) → `V=on`.

## 막힐 때
- 서명이 계속 틀린다: 본문을 객체로 바꿨다가 다시 직렬화하면 공백·숫자 모양이 바뀝니다. 바이트 그대로 계산합니다.
- 웹훅이 503 「서명을 확인할 수 없음」: 앱이 OpenBao에서 비밀을 못 읽었습니다. `make up`(openbao-init이 `secret/daon/payment-webhook`을 넣고 정책을 고칩니다).
- 결제 버튼이 404: `web/html/app.js`를 바꾸지 않았거나 브라우저 캐시입니다.
- 웹훅이 mall-portal에 닿지 않는다(`/v1/webhooks`의 status가 오류 이름): 결제사 스텁과 mall-portal이 같은 `app` 망에 있는지(A1) 봅니다. 콜백 주소는 `daon.payment.callback-url`(기본 `http://mall-portal:8085/pay/webhook`).
- Express: `diffs/s10-04/express.diff`는 E26(`createPaymentIntent.ts`에 주문 소유 확인과 `Idempotency-Key`). EverShop의 Stripe·PayPal 웹훅은 이미 서명과 멱등을 갖췄습니다(좋은 예).

## 남는 이벤트
`payment.denied.client_call`(WARN, actor `member:<ID>`), `payment.denied.bad_signature`(WARN, actor `anonymous`), `payment.duplicate.event`(**INFO**, target `payment:<결제 번호>`), `payment.denied.amount_mismatch`(WARN, target `order:<ID>`, 금액 값은 넣지 않음), `payment.denied.bad_transition`(WARN, reason 「status=0 조건 0행」).
