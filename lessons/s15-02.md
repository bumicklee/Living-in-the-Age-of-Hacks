# 15-2 캡스톤 ②: 대응과 복구
⏱ 약 12분 · 고칠 파일: 자바 1곳(✏️ `DaonIncidentController`: 직원 격리·비밀번호 초기화·골라 복구) + 승인 서비스 정책(✏️ `policy.yml`·`ApprovalPolicy`·`approval-init.sh`) + 경보 규칙 1개(✏️ `infra/observability/rules/change.yaml`) · 랩 도구 `python -m daon incident|keys|tokens`·`make evidence`·`make restore-columns`·`make capstone PART=status`

**첫 줄: `make wipe` 금지.** 15-1의 사고 상태 그대로 이어 갑니다. 지난 수업에서 범위를 찾았으니, 이번에는 그 범위만큼 정확히 되돌립니다.

## 따라 하기
1. **지금 상태(레드).** 새어 나간 비밀번호로 아직 로그인됩니다. 사고 때 받은 토큰도 살아 있습니다. 주문 20건의 주소가 바뀐 채입니다.
   ```bash
   make goto L=15-2 && make up STACK=spring
   make capstone PART=status
   ```
2. **대응 순서(격리 → 증거 → 교체 → 폐기 → 정리 → 복구 → 강화).** 고위험 기능이라 admin의 권한 상승(13-6, 묶음 `incident-response`)이 먼저입니다.
   - ① **격리**: `python -m daon incident lock --admin staff_night` (✏️ 14-4의 `lock-actor`를 직원 계정에도: 상태 0, 관리자 캐시, 관리자 토큰 계정 단위 폐기)
   - ② **증거 보존(복구보다 먼저)**: `make evidence INCIDENT=capstone`
   - ③ **자격증명 교체**: `python -m daon incident reset-password --admin staff_night`(임시 비밀번호는 화면에 찍지 않습니다) · 관리자 서명키 회전 `python -m daon keys rotate` → 모두 다시 로그인한 뒤 `python -m daon keys retire`. **누구 토큰이 새었는지 모르면 키를 바꾸고, 알면 그 토큰만 폐기합니다.**
   - ④ **토큰 폐기**(회전하지 않는 경우의 절차): `python -m daon tokens revoke --admin staff_night`
   - ⑤ **시크릿 정리**: 저장소에서 지우는 것보다 비밀번호를 바꾸는 것이 먼저입니다(6-2). 이력 정리는 그다음, 선택.
   - ⑥ **골라 복구**: 전체 되돌리기가 아니라 감사 로그로 찾은 주문의 받는 사람 칸만.
     ```bash
     make restore-columns ACTOR=admin:staff_night SINCE=<사고 시작 UTC>      # 표만: 백업 값·지금 값·사고 뒤 정상 변경
     make restore-columns ACTOR=admin:staff_night SINCE=<…> APPLY=1 CONFIRM=<확인한 주문,…>
     ```
     사고 뒤 고객 요청으로 다시 바뀐 주문은 빼야 합니다(도구가 멈춥니다). 되돌린 쓰기도 감사 로그(`incident.restore.columns`)에 남습니다.
   - ⑦ **정책 강화**: ✏️ 승인 서비스 `policy.yml`에 `refund.dual_after_receiver_change_hours: 72`(받는 사람을 바꾼 주문은 72시간 동안 금액과 관계없이 두 사람 승인) · ✏️ 경보 규칙 `change.yaml`(한 직원이 1시간에 받는 사람 정보를 10건 넘게 바꾸면 P2). 사고 뒤 24시간 「모든 환불 두 사람」 한시 규칙은 런북 절차로 둡니다.
3. **확인합니다.**
   ```bash
   make up STACK=spring           # 승인 서비스·관리자 앱 다시 빌드
   make capstone PART=1           # 다시 돌리기: 2단계(로그인)에서 멈춰야 합니다
   make capstone PART=status      # 손으로 한 대응 ①~⑤
   make check L=15-2              # 따로 쓰는 점검용 시나리오(staff_drill)로 사고 → 정답 대응 → 확인을 처음부터 돈다
   make check-all && make score   # 사고가 났다고 점수판이 바뀌지 않는다. 바뀐 것은 데이터와 자격증명이다
   ```
4. **통지문과 회고.** 14-6 양식(`docs/templates/breach-*.md`)을 15-1 결과로 한 번 채워 봅니다(법률 자문 아님). 회고 양식 `docs/templates/회고.md`의 마지막 칸 「점검표에 더할 줄」이 15-4로 이어집니다.

## 막힐 때
- 서명키 회전 뒤 관리자 웹이 계속 401: 브라우저에 남은 옛 토큰입니다. 다시 로그인합니다.
- 골라 복구가 고객이 직접 바꾼 주소까지 덮어쓰려 한다: 「사고 뒤 정상 변경」 칸을 보고 그 주문을 `CONFIRM`에서 뺍니다.
- `make wipe`를 해서 15-1 상태가 사라졌다: `make capstone RESET=1` 뒤 `make capstone PART=1`부터 다시.
- 처음부터 다시 연습: `make capstone RESET=1`(직원 잠금·비밀번호·받는 사람 칸·서명키 폐기를 처음으로).
- Express: 같은 대응이 EverShop에도 있습니다(관리자 세션 파기, 쿠키 서명값 교체 E01, PostgreSQL 백업에서 골라 복구).

## 확인 문제
1. 증거 보존을 골라 복구보다 먼저 하는 이유는? (복구가 데이터를 바꾸므로, 바꾸기 전 상태를 먼저 남겨야 조사·신고에 쓸 수 있다.)
2. 키 회전과 토큰 폐기는 언제 각각 쓰나? (어떤 토큰이 새었는지 모르면 키를 회전해 모두 무효로, 특정 토큰만이면 그 토큰만 폐기 목록에.)
3. 회고의 「점검표에 더할 줄」 예 하나는? (「관리자 정상 권한 행위 중 고객 정보·배송지 변경 건수에 경보가 있는가」.)
