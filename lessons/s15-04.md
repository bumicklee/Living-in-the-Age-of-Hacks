# 15-4 최종 소스 받기와 내 서비스에 secure-kit 적용하기
⏱ 약 11분 · 고칠 파일: 가게 예제 Spring(✏️ `pom.xml` 의존성 한 줄 · `application.yml` · `@RateLimited("login")` · `@Audited`) · Express(✏️ `package.json` · `app.js`) · 견본 보고서 ✏️ `packages/examples/점검-보고서-견본.md` · 랩 도구 `make kit-up`·`make kit-contract`

이제 다온마켓이 아니라 여러분 회사의 서비스를 볼 차례입니다. 「고치기 전에 먼저 점검한다」는 뼈대를 그대로 가져갑니다.

## 폴더 지도
- `spring/`·`express/`: 고친 포크(라이선스 Apache-2.0 · GPL-3.0을 따릅니다)
- `packages/secure-kit-spring/`·`packages/secure-kit-express/`·`packages/secure-kit-evershop/`: 부품 24개(**MIT**, 회사 코드에 넣어도 됩니다). 목록 `packages/parts.yaml`
- `packages/contract-tests/`: 두 스택 공통 계약 시험(`CONTRACT.md`가 주소·응답·이벤트 이름을 정합니다)
- `packages/examples/`: 부품 예제(`spring-kit-demo`·`express-kit-demo`, 부품 24개 전부)와 가게 예제(`spring-shop`·`express-shop`, 이 수업)
- `docs/templates/`: 최초 점검 보고서·런북·통지문·회고·사고 30분 정리 양식

## 따라 하기
1. **가게 예제를 띄우고 점검합니다(부품을 붙이기 전).**
   ```bash
   make goto L=15-4
   make kit-up APPS=spring-shop,express-shop      # 처음에는 Maven·npm 내려받기(수 분)
   make check L=15-4                              # 레드: 오류 응답에 내부 문구, 로그인 제한 없음, 감사 기록 없음
   ```
2. **내 서비스의 「최초 점검 보고서」를 씁니다.** 양식 `docs/templates/최초-점검-보고서.md`. 가게 예제를 「내 서비스」 대신 점검해 세 줄을 채웁니다(오류 응답의 내부 문구 낮음 · 로그인 속도 제한 없음 높음 · 관리자 조회 감사 로그 없음 중간) → ✏️ `packages/examples/점검-보고서-견본.md`.
   - 실행 점검은 **자기 서비스의 시험 환경에서, 허락을 받고, 읽기 요청만** 합니다.
3. **보고서 순서대로 부품을 붙입니다.** 넣는 법은 세 가지뿐입니다: 설정만 켜기 / 한 줄 / 안전한 부품으로 바꿔 쓰기.
   ```bash
   mvn -f packages/secure-kit-spring/pom.xml install    # 로컬 설치 판(Maven Central이 아닙니다). make kit-up이 컨테이너 안에서 대신 해 줍니다
   ```
   - Spring: ✏️ `pom.xml`에 `secure-kit-spring-boot-starter` 한 줄 → ✏️ `application.yml`에 `secure-kit.error-response.enabled: true`, `secure-kit.rate-limit.login` → ✏️ 로그인에 `@RateLimited("login")`, 회원 상세에 `@Audited(action = "member.read", resource = "member")`
   - Express: ✏️ `package.json`에 `@secure-kit/express` → ✏️ `kit.errorResponse()`, `kit.rateLimit('login')`, `kit.audited('member.read')`. 설정 키가 Spring과 같습니다
   - 붙인 뒤 보고서 세 줄의 처리 결과를 「고침」으로, 근거에 계약 시험 이름을 적습니다.
4. **확인합니다.**
   ```bash
   make check L=15-4               # 두 가게 앱이 같은 계약 셋을 통과 · 견본 보고서 · 부품 예제 24개 × 두 스택(정상)
   make kit-contract               # 계약 시험 전부(부품 24개 + 가게 셋 + 목록 정적 확인)
   ```

## 막힐 때
- secure-kit을 Maven Central·npm에서 찾는다: 지금은 저장소 안의 소스입니다(Maven 로컬 설치, npm `file:` 경로).
- 회사 서비스가 Spring Boot 2.x다: 부품은 Spring Boot 3.2 이상·Java 17 이상입니다. 맞지 않으면 손으로 쓴 수업 코드를 참고합니다.
- 실행 점검을 운영 서비스에 바로 한다: 하지 않습니다. 시험 환경, 허락, 읽기 요청만.
- 랩의 방어 스위치(`enabled`)는 영상용입니다. 회사 서비스에서는 보호를 끄는 스위치를 운영에 두지 않는 편이 낫습니다.
- 부품으로 안 되는 것: 소유권(조회 조건), 대량 할당(요청 전용 DTO), 경쟁 조건(조건부 UPDATE·유니크 제약), 원장 대사, 아키텍처는 패턴·레시피로 가져갑니다.

## 확인 문제
1. 최초 점검 보고서에 「잘 된 것」 절을 두는 이유는? (이미 안전하다고 확인한 곳을 기록해 다음 점검이 같은 곳을 다시 보지 않게, 좋은 예로 쓰려고.)
2. 실행 점검에서 지킬 세 가지는? (자기 서비스의 시험 환경, 허락, 상태를 바꾸지 않는 읽기 요청만.)
3. secure-kit으로 막을 수 없어 패턴으로 가져가야 하는 것 두 가지는? (소유권 검사, 경쟁 조건.)
