# 11-3 요청 밀반입: 게이트웨이와 앱이 경계를 다르게 본다
⏱ 약 11분 · 고칠 파일 설정 3개(`infra/arch.txt`·`infra/gateway/nginx.conf`·새 `infra/compose.a07.yml`) + 새 폴더 `infra/varnish/` · 아키텍처 **A7** · 방어 스위치 없음(구조·설정)

앞단(게이트웨이)과 뒷단(캐시·앱)이 요청의 끝을 다르게 세면, 요청 하나 안에 다른 요청이 숨어 들어갈 수 있습니다. 이 수업은 그 **조건**을 설정에서 없앱니다.

> 안전 원칙: 이 수업은 공격 요청을 보내지 않습니다. 재연은 **설정 점검**입니다. `make check`의 「방어 확인」 시험 세 개만 모호한 모양의 요청을 보내 「400으로 끊기는가」를 봅니다. 그 요청의 본문에는 다른 요청이 없습니다(길이 표시 둘은 두 해석이 같은 곳에서 끝나게 만든 것, 나머지는 본문 없음).

## 따라 하기
1. **레드부터 봅니다.**
   ```bash
   make goto L=11-3
   make audit-gateway         # 고칠 것 4개: 고객 API 입구 없음 · 거절 규칙 없음 · 거절 이벤트 없음 · 이미지 태그만 고정
   make replay T=29           # 같은 표 [레드]
   make check L=11-3
   ```
2. **A7을 붙입니다(✏️ `infra/arch.txt`에 `a07`, 새 `infra/compose.a07.yml`).** 게이트웨이에 고객 API 입구 8086을 엽니다: PC → `gateway:8086 /api/` → `varnish:6081` → `mall-portal:8085`. Varnish(캐시)는 11-4에서 다룹니다. 고객 웹(8088)과 앱 직접 주소(8085)는 그대로 둡니다.
3. **모호한 요청 거절(✏️ `infra/gateway/nginx.conf`).**
   - nginx는 1.21.1부터 Content-Length와 Transfer-Encoding이 함께 온 요청, Content-Length 두 줄, 이름에 공백이 있는 헤더(접힌 헤더 줄)를 스스로 400으로 끊습니다. **버전을 고정해** 이 동작을 지킵니다.
   - 같은 규칙을 설정에도 적습니다(두 번째 겹): `map`으로 「길이 표시 둘」·「chunked가 아닌 Transfer-Encoding」을 고르고 `return 400`.
   - 본문은 앞단이 끝까지 받은 뒤 길이를 다시 정해 넘깁니다(`proxy_request_buffering on`, 기본값. 끄지 않습니다).
   - 뒷단 연결은 요청마다 새로 엽니다(`proxy_set_header Connection "close"`). nginx 1.29.7부터는 재사용이 기본입니다. 한 연결을 여러 사용자가 나눠 쓰지 않게 합니다.
4. **버전 고정(✏️ `compose.a07.yml`).** 게이트웨이·Varnish 이미지를 `태그@sha256:다이제스트`로 고정합니다(7-6과 같은 이유: 태그는 같은 이름에 다른 내용을 올릴 수 있다). 올릴 때는 태그와 다이제스트를 함께 바꿉니다.
5. **뒷단 HTTP/2는?** `make audit-gateway`의 [실측] 줄이 실행 중 nginx가 `proxy_http_version 2`를 받아들이는지 봅니다. 받아들여도 Varnish의 뒷단(앱 쪽)은 HTTP/1.1만 씁니다. 그래서 이 랩은 「모호한 요청 거절 + 버전 고정」으로 갑니다. 끝까지 HTTP/2로 가려면 캐시를 빼거나 HTTP/2 뒷단을 지원하는 캐시가 필요합니다.
6. **앱 쪽은 확인만.** Tomcat 10.1은 잘못된 헤더를 거절합니다(느슨하게 바꾸는 설정이 없는지 점검표가 봅니다). Node(EverShop)는 `insecureHTTPParser`를 켜지 않고 `node:x.y.z`로 고정합니다.
7. **⑤ 탐지.** 게이트웨이가 스스로 끊은 요청(400·501, 뒤 서버로 가지 않음)은 `request.denied.malformed` 한 줄을 남깁니다. nginx `log_format`으로 앱 SECURITY 줄과 같은 키를 맞추고 줄 앞에 `WARN SECURITY`를 붙여, 8-4 수집기가 같은 흐름으로 모읍니다.
8. **확인합니다.**
   ```bash
   make up STACK=spring
   make audit-gateway         # 모두 확인
   make replay T=29           # [그린]
   make check L=11-3          # 6개(정상 2개: 로그인·상품 목록·주문 상세, 정상 청크 전송이 A7 경로로 통과)
   make logs S=gateway | grep request.denied.malformed
   make mem                   # Varnish 몇 MB인지 적어 둡니다
   make check-all             # 섹션 2~10 시험이 그대로 그린인지
   ```

## 막힐 때
- 점검 스크립트가 설정 파일만 읽으면 실행 중 컨테이너와 다를 수 있습니다. `make audit-gateway`는 실행 중 게이트웨이의 `nginx -T`·이미지·버전을 읽습니다.
- `make up`에서 다이제스트를 받지 못한다: 이미지 저장소에 닿지 않는 PC입니다. 같은 태그가 이미 받아져 있으면 `docker image inspect nginx:1.30.6-alpine`의 `RepoDigests`와 비교합니다.
- Express: `diffs/s11-03/express.diff`는 Node HTTP 서버를 `{ insecureHTTPParser: false, requireHostHeader: true }`로 만듭니다(기본값을 설정에 적어 둠).

## 남는 이벤트
`request.denied.malformed`(WARN, 게이트웨이). 경보 후보: 같은 IP 3회 / 10분.
