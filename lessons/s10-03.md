# 10-3 결제 웹훅이 두 번 오면: NatWest·Chase 이중 처리
⏱ 약 7분 · 사고 수업(랩 실행 없음, `make check` 없음) · 마지막 2분은 10-4 시작 지점 코드 화면

## 따라 하기
1. **사고 두 개를 봅니다.** 은행 계좌에서 같은 거래가 두 번 처리된 일이 있었습니다(NatWest 2022, JPMorgan Chase 2023-06). 두 사고 모두 **원인은 공개되지 않았습니다.** 「웹훅 때문」이라고 말하지 않습니다. 같은 돈 이벤트가 두 번 처리되는 구조를 보여 주는 예로만 씁니다.
2. **같은 이벤트가 두 번 오는 세 갈래 길.** ① 결제사 재전송(응답이 늦거나 4xx를 받으면 다시 보냄) ② 우리 쪽 배치 재처리 ③ 사용자 재시도. 결제사 문서는 웹훅이 두 번 이상 올 수 있다고 안내합니다.
3. **원리 세 줄.** 이벤트 ID 유니크 · 멱등 키 · 단방향 상태 전이. 「서명 확인은 보낸 사람을, 중복 확인은 처음인지를 확인한다」.
4. **다온마켓에서 결제 상태를 바꾸는 입구를 짚습니다.**
   ```bash
   make goto L=10-4
   grep -n "paySuccess" spring/mall-portal/src/main/java/com/macro/mall/portal/controller/OmsPortalOrderController.java
   grep -n "alipay" spring/mall-portal/src/main/resources/application.yml
   curl -s -X POST 127.0.0.1:9101/v1/payments/PAY000001/resend   # 가짜 결제사: 같은 웹훅을 한 번 더(받는 곳은 아직 없다)
   ```
   - 고객이 부르는 `POST /order/paySuccess`(로그인한 회원 누구나, 남의 주문도)
   - 로그인 없이 열린 `/alipay/**`(알림 금액 대조·중복 기록 없음, 조회 API 공개)
   - 아직 없는 웹훅 수신 자리(10-4에서 만든다)

## 확인 문제
1. 서명이 맞는 웹훅이 두 번 왔다. 두 번째는 위조인가? → 아니다. 정상 재전송일 수 있다. 처음인지는 이벤트 ID로 판단한다.
2. NatWest 사고의 원인은? → 공개되지 않았다. 추정으로만 말한다.
3. 다온마켓에서 고객이 직접 부를 수 있는 결제 상태 입구는? → `/order/paySuccess`.

## 남는 이벤트
없음. 10-4에서 `payment.duplicate.event`·`payment.denied.amount_mismatch` 등을 심습니다.
