# 13-4 두 사람 승인·별도 경로 확인·지연 실행
⏱ 약 11분 · 고칠 파일 승인 서비스 `ApprovalController.approve()` + 새 파일 3개(`OutOfBandConfirm`·`DelayedExecutionScheduler`·`PayoutCircuitBreaker`) + 관리자 앱 새 `DaonApprovedRefundPoller` · 아키텍처 A10 그대로 · 방어 스위치 `dual-approval`

사람 수를 늘려도 그 사람들의 권한이 한 곳에 모이면 소용없습니다. 고액은 **다른 역할의 두 번째 사람**이, **다른 경로(메일)**로 받은 번호로 승인하고, **바로 실행하지 않고 취소할 시간**을 둡니다. 나가는 양이 기준을 넘으면 **자동 실행을 멈춥니다**.

> 숫자(고액 300,000원, 지연 10초, 시간당 6건·1,000,000원)는 모두 가짜 기준입니다. 회사 기본 지연은 30분입니다(`policy.yml`).

## 따라 하기
1. **레드부터 봅니다.**
   ```bash
   make goto L=13-4
   make up STACK=spring
   make replay T=34 PART=high-value   # 가짜 고액 주문에 400,000원, 한 사람이 바로 [레드]
   make check L=13-4
   ```
2. **두 번째 사람(✏️ `ApprovalController.approve()`).** 고액이면 `PENDING_SECOND`. 승인자는 요청자와 달라야 하고(같으면 403 + `approval.denied.self_approval`), 역할이 `재무 담당`이어야 합니다(역할은 승인 서비스가 DB에서 다시 읽습니다).
3. **다른 경로(✏️ `OutOfBandConfirm`).** 첫 요청 때 6자리 번호를 `SecureRandom`으로 만들어 **Mailpit 메일로만** 보냅니다. 저장은 해시만, 5분·한 번만·5번 틀리면 끝. 승인 API 응답에는 넣지 않습니다(4-5에서 배운 것). 틀리면 `approval.denied.bad_confirm`.
4. **지연 실행(✏️ `DelayedExecutionScheduler`).** 두 번째 승인 뒤 `SCHEDULED`, `execute_after = 지금 + 10초`. 그동안 요청자·승인자·취소 역할 누구나 `POST /approvals/{id}/cancel`(→ `approval.cancelled.in_window`). 창이 끝나면 `READY`가 되고, 관리자 앱의 `DaonApprovedRefundPoller`가 3초마다 가져가 13-3의 실행기로 실행합니다. 승인 토큰은 창이 끝난 뒤에만 나갑니다.
5. **출금 서킷 브레이커(✏️ `PayoutCircuitBreaker`).** 토큰을 내주기 직전에 지난 1시간의 건수·합계를 읽고, 넘으면 `OPEN` + `payout.breaker.open`. 이후 요청은 `HELD`. 닫기는 자동이 아니라 **서로 다른 두 사람**(`POST /breaker/close`를 재무 담당·운영 책임이 한 번씩). 9-5의 서킷 브레이커와 원리는 같고 대상이 「돈이 나가는 양」입니다.
6. **확인합니다.**
   ```bash
   make up STACK=spring
   make replay T=34 PART=high-value   # 두 번째 승인 대기 · 스스로 승인 403 · 환불 0건 [그린]
   make check L=13-4                  # 7개(정상 1개: 고액 기준 미만은 바로 실행). 지연을 기다려 1분쯤 걸린다
   open http://127.0.0.1:8025         # 「[다온 승인] 확인 번호」 메일(번호는 화면에서 일부 가림)
   make approval-status
   ```
7. **스위치.** `make switch K=dual-approval V=off` → `make replay T=34 PART=high-value` 레드 → `V=on`.

## 막힐 때
- 확인 번호 메일이 안 온다: 승인 서비스가 Mailpit(1025)에 닿는 망(app)에 붙었는지, `make logs S=approval | grep 13-4`.
- 시험이 지연을 기다리다 시간 초과: 지연은 10초, 실행기는 3초마다 봅니다. 30초 안에 환불이 없으면 `make logs S=mall-admin | grep 13-4`.
- 브레이커가 열린 채다: 서로 다른 두 사람이 닫아야 합니다. 랩에서 처음부터 하려면 `make approval-reset`.
- 「두 사람이 공모하면?」: 막지 못합니다. 그래서 지연 창에 다른 역할도 취소할 수 있게 하고, 브레이커가 양을 제한하고, 13-6의 접근 기록이 사후 추적을 맡습니다.
- 고액 기준 미만도 두 사람 승인을 거치게 하면 승인 피로가 생깁니다. 승인자가 내용을 안 보고 누르면 다시 블라인드 승인입니다.
- Express: `diffs/s13-04/express.diff`는 환불 라우트가 `202 Accepted`와 승인 상태(`PENDING_SECOND`·`SCHEDULED`·`CANCELLED`)를 돌려주고, 관리자 화면 `RefundButton`이 그 상태를 보여 주게 바꿉니다.

## 남는 이벤트
`approval.denied.self_approval`(WARN, 한 번이라도) · `approval.denied.bad_confirm`(WARN, 같은 사람 3회/10분) · `approval.pending.second_approver`(INFO, 감사용) · `approval.cancelled.in_window`(INFO, 한 번이라도) · `payout.breaker.open`(WARN, 즉시 P1).
