# 13-6 운영 접근: 기기 신뢰·필요할 때만 권한·접근 기록
⏱ 약 8분 · 고칠 파일 자바 4곳(관리자 앱 `UmsAdminServiceImpl.login()`·`DaonStaffSeed`, secure-kit `DynamicAuthorizationManager`, 승인 서비스 새 `ElevationController`) + 새 파일 3개(`OpsElevationGate`·`DaonOpsElevationService`·`DaonElevationController`) · 아키텍처 A10 그대로(권한 상승 승인에 재사용) · 방어 스위치 `ops-elevation`

권한 상승의 네 요소: **사유, 다른 사람의 승인, 시간 제한, 기록.** 공용 계정과 데모 계정은 **지우지 않고 닫습니다**. 그 이름으로 들어오는 시도 자체가 신호가 됩니다.

> 안전 원칙: 공용 계정·데모 계정·직원은 모두 가짜이고 비밀번호는 화면에 찍지 않습니다. 고위험 기능 시험은 관리자 역할을 **같은 값으로** 다시 쓰는 요청이라 바뀌는 것이 없습니다.

## 따라 하기
1. **레드부터 봅니다.**
   ```bash
   make goto L=13-6
   make up STACK=spring
   make replay T=35        # ① daon_ops 로그인 ② macro 로그인 ③ admin이 권한 상승 없이 관리자 역할 변경 [레드]
   make check L=13-6
   ```
2. **계정 정리(✏️ `DaonStaffSeed.apply()`).** 공용 계정 `daon_ops`와 원본 데모 관리자를 `status=0`(닫힘)으로. 앱이 뜰 때 맞춥니다. `admin`은 이 랩의 도구·시험이 쓰는 계정이라 열어 둡니다. 대신 아래 3번 때문에 `admin`도 고위험 기능은 권한 상승을 거쳐야 합니다(회사라면 `admin`도 닫습니다).
3. **로그인(✏️ `UmsAdminServiceImpl.login()`).** 닫힌 계정이면 **틀린 비밀번호와 같은 문구**로 거부하고(4-4 원칙) `auth.denied.disabled_account`. 비밀번호 비교는 그대로 한 번 해서 응답 시간도 같게 둡니다.
4. **고위험 기능(✏️ secure-kit `OpsElevationGate`·`DynamicAuthorizationManager`).** 관리자 계정·역할·권한표를 바꾸는 POST(`/admin/role/update`, `/admin/update/**`, `/role/**`, `/resource/**` …)는 역할이 있어도 **살아 있는 권한 상승**이 있어야 통과합니다. 없으면 403 + `ops.denied.no_elevation`.
5. **권한 상승(✏️ 승인 서비스 `ElevationController`, 관리자 앱 `DaonElevationController`·`DaonOpsElevationService`).**
   - 요청: `POST /daon/elevation/request` `{"reason":…, "group":"admin-accounts", "minutes":30}`(사유 필수, 최대 60분).
   - 승인: 다른 사람(`운영 책임`)이 승인 서비스에서 `POST /elevations/{id}/approve`. 요청자 스스로는 403 + `approval.denied.self_approval`.
   - 켜기: `POST /daon/elevation/{id}/activate` → 승인 서비스가 서명한 권한 상승 토큰(누가·묶음·만료)을 13-3과 같은 방법으로 확인하고 만료 시각까지 켭니다. `ops.elevation.granted`(INFO, 사유는 승인 서비스 표에만).
6. **기기 신뢰(그림).** 관리자 입구(8443)에서 사람(로그인)과 기기(클라이언트 인증서)를 둘 다 확인하는 그림만 봅니다. 12-3의 파트너 입구 mTLS와 같은 장치입니다.
7. **확인합니다.**
   ```bash
   make up STACK=spring
   make replay T=35        # 셋 다 막힘 [그린]
   make check L=13-6       # 7개(정상 2개: 일상 업무는 권한 상승 없이 · 본인 비밀번호 변경은 현재 비밀번호 필요)
   make logs S=mall-admin | grep -E "disabled_account|no_elevation|elevation.granted"
   ```
   시험은 랩 시계(A13)를 31분 밀어 만료 뒤 403을 봅니다(끝나면 되돌림).
8. **스위치.** `make switch K=ops-elevation V=off`(앱이 다시 뜨며 계정도 다시 열림) → `make replay T=35` 레드 → `V=on`.

## 막힐 때
- 계정을 닫았더니 관리자 웹 일부 화면이 깨진다: 계정은 지우지 않고 닫았으니 작성자 칸은 그대로입니다. 캐시(Redis)에 옛 상태가 남았으면 앱이 뜰 때 지웁니다.
- 권한 상승 승인자가 없다: 시드 직원 `staff_lead`(운영 책임)를 씁니다.
- 권한표 캐시에 옛 권한이 남아 있다: 6-4에서 권한을 DB에서 읽게 바꿨는지 봅니다.
- F11(다른 관리자 비밀번호를 수정 API로 바꾸기)은 4-7에서 이미 막았습니다. 이 수업에서는 그 API가 고위험 묶음에 들어가 권한 상승까지 요구하게 됩니다.
- 한 달에 한 번 권한 상승 목록(승인 서비스 표 `daon_approval_request`의 `ops-elevation`)을 팀이 같이 봅니다(8-7 경보 대응표에 한 줄).
- Express: `diffs/s13-06/express.diff`는 관리자 토큰 속 역할을 그대로 믿지 않고(E21) DB의 역할과 권한 상승 만료 시각을 다시 읽게 바꿉니다.

## 남는 이벤트
`auth.denied.disabled_account`(WARN, 한 번이라도 P1) · `ops.denied.no_elevation`(WARN, 같은 사람 3회/10분) · `ops.elevation.granted`(INFO, 감사용·14장 타임라인) · `approval.denied.self_approval`(13-6).
