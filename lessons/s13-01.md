# 13-1 바이낸스 64억 달러: 키를 훔치지 않고 서명을 시켰다
⏱ 약 10분 · 사고 수업(고치기 없음, `make check` 없음) · 아키텍처 변화 없음 · 재연 T34(13-3에서)

키를 금고(HSM·서명 시스템)에 잘 넣어 두어도, 금고 앞 창구가 **들어온 종이를 읽지 않고 도장을 찍으면** 소용없습니다. 「키를 지키는 것」과 「무엇에 서명하는지 아는 것」은 다른 문제입니다.

> 숫자는 출처마다 다릅니다(약 63억~64억 달러). 화면 자막에 「TRM 기준」·「Elliptic 기준」처럼 출처를 붙입니다. 「서명 시스템이 공격자가 고른 거래에 서명했다」는 분석 회사의 **분석**이고, 회사의 공식 원인 보고서는 아직 없습니다. 위임 서명을 만드는 방법·쓸어 가기 구조·세탁 경로는 다루지 않습니다.

## 따라 하기
1. **사고의 네 단계를 다온마켓으로 옮겨 그립니다(영상의 그림).**
   | 사고 | 다온마켓 |
   |---|---|
   | 개발자 노트북 | 관리자 PC(관리자 웹 8090에 로그인한 직원) |
   | 서명 시스템 | 관리자 앱의 반품 승인 API `POST /returnApply/update/status/{id}` |
   | 위임 승인 50건 | 승인 한 번에 금액·처리자를 **요청이** 정함 |
   | 동시다발 출금 | 가짜 결제사 환불(13-3에서 붙는 교육용 실행기) |
2. **같은 모양의 코드를 찾습니다(마지막 1분).**
   ```bash
   make goto L=13-1
   ```
   `spring/mall-admin/.../service/impl/OmsOrderReturnApplyServiceImpl.java`의 `updateStatus()`에서 두 줄을 봅니다.
   `setReturnAmount(statusParam.getReturnAmount())` · `setHandleMan(statusParam.getHandleMan())`
   승인하는 쪽이 금액을 직접 읽지 않고, 요청이 준 숫자를 그대로 적습니다(점검표 F48).
3. **점수판을 봅니다.** `make score` → 남은 취약에 T34·T35가 있습니다.

## 막힐 때
- 「블록체인 얘기라 우리와 상관없다」: 「서명」을 「승인 버튼」으로 바꿔 읽어 보세요. 결제 취소·환불·정산·권한 부여가 모두 같은 구조입니다.
- EIP-7702가 궁금하면 사고 자료 글만 봅니다. 수업은 「위임 한 번으로 계속 쓸어 가는 권한이 남았다」까지입니다.

## 확인 문제
1. 키가 유출되지 않았는데도 돈이 나간 이유를 한 문장으로 쓰세요. (서명 시스템이 요청받은 거래가 무엇인지 스스로 따지지 않고 서명했다고 분석 회사들이 봅니다.)
2. `updateStatus()`에서 승인하는 쪽이 직접 읽어야 하는데 요청에서 받는 값 두 개는? (`returnAmount`, `handleMan`)
