# 9-2 실패하면 통과시키는 코드(fail-open) + 401로 둔갑한 장애(점검 F46)
⏱ 약 11분 · 고칠 파일 자바 4개(`DaonStepUpClient`·`DaonSmsVerifyController`·`GlobalExceptionHandler`·`SecurityConfig`) · 아키텍처 변화 없음 · 방어 스위치 `fail-closed`·`error-path`

## 따라 하기
1. **레드부터 봅니다.**
   ```bash
   make goto L=9-2
   make stub-fault S=sms MODE=500      # 가짜 문자 스텁이 모든 요청에 500
   make replay T=22                     # 틀린 번호(000000)로 「본인 확인을 마쳤습니다」 [레드]
   make stub-fault S=sms MODE=ok
   make replay T=46                     # 가격 없는 장바구니로 주문 → HTTP 401 [레드]
   make logs S=mall-portal | grep -A3 NullPointerException   # 같은 시각, 진짜 원인
   make check L=9-2
   ```
2. **fail-closed(✏️ `mall-portal/.../component/DaonStepUpClient.java`).**
   - `catch (Exception e) { return true; }`를 지웁니다. 사업자 오류(200이 아닌 응답·이상한 본문)·시간 초과·연결 실패는 `DependencyUnavailableException`(「확인 불가」)으로 던집니다.
   - 연결·응답 시간 제한 2초를 코드에 적습니다(HttpClient 기본값은 제한이 없습니다).
   - 「번호가 틀림」(`valid=false`)은 그대로 `false`입니다. 두 경우를 섞지 않습니다.
3. **응답을 나눕니다(✏️ `DaonSmsVerifyController.java`).** 「확인 불가」는 HTTP 503 「잠시 뒤 다시 시도해 주세요」, 틀린 번호는 400. 고객 불편을 줄이는 길은 통과가 아니라 다시 시도 안내와 다른 수단입니다.
4. **오류 경로(F46, ✏️ `mall-security/.../config/SecurityConfig.java`, `mall-common/.../exception/GlobalExceptionHandler.java`).**
   - 보안 설정에서 ERROR 디스패치와 `/error`를 로그인 없이 엽니다. `/error`는 오류 응답만 만들고 데이터에 닿지 않습니다.
   - `GlobalExceptionHandler`에 마지막 처리기 `@ExceptionHandler(Exception.class)`: HTTP 500, 본문 `{"code":500,"message":"일시적인 오류입니다","trace_id":"…"}`(헤더 `X-Trace-Id`는 원래 붙습니다). 예외 문구·클래스 이름은 응답에 넣지 않습니다(6-5).
   - Spring이 상태 코드를 아는 예외(404·405·400 등 `ErrorResponse`), 멀티파트 예외, Spring Security 예외는 그대로 던져 원래 처리에 맡깁니다. 재인증·속도 제한 처리기는 우선순위가 높아 먼저 고릅니다.
   - 가격 검사는 넣지 않습니다. 가격 입력 자체는 10-8에서 없앱니다(이 수업은 장애가 401로 둔갑하는 오류 경로만 고칩니다).
5. **확인합니다.**
   ```bash
   make up STACK=spring
   make stub-fault S=sms MODE=500 && make replay T=22 ; make stub-fault S=sms MODE=ok   # 503 [그린]
   make replay T=46                     # HTTP 500 + trace_id [그린] (주문은 여전히 실패: 10-8)
   curl -s -H "Authorization: Bearer <alice 토큰>" 127.0.0.1:8085/daon/lab/boom   # 랩 전용 경로: 500 + trace_id
   make check L=9-2                     # 9개(정상 3개 포함)
   ```
   그 trace_id로 Grafana(`{app="mall-portal"} |= "<trace_id>"`)에서 스택 줄을 바로 찾습니다.
6. **스위치.** `make switch K=fail-closed V=off` → `make check L=9-2` 레드(T22) → `V=on`. `K=error-path`는 F46.

## 막힐 때
- `make check`가 스텁 장애를 알린다: 다른 창에서 켠 장애가 남은 것입니다. `make stub-fault S=sms MODE=ok`.
- `/daon/lab/boom`이 404: 랩 설정(`infra/compose.lab.yml`의 `DAON_LAB_BOOM=true`)이 들어간 mall-portal인지 봅니다. 운영 코드에는 남기지 않는 경로입니다.
- 마지막 처리기를 넣었더니 다른 수업 시험의 404·403이 500이 됐다: `passThrough`(ErrorResponse·보안 예외 그대로 던지기)를 빠뜨렸는지 봅니다.
- Express: `diffs/s9-02/express.diff`는 API 오류 처리기의 상태 코드 정리(4xx만 그대로, 나머지는 500 + trace_id)와 같은 문자 스텁을 부르는 `verifySmsCode()`의 fail-closed입니다. EverShop은 장바구니 가격을 서버 값으로 써서 F46 같은 NPE는 없습니다(좋은 예).

## 남는 이벤트
`auth.fail_closed.dependency_error`(WARN, actor `member:<ID>`, target `dependency:sms-stub`). 처리되지 않은 예외는 SECURITY가 아니라 로거 `OPS`의 `error.unhandled`(ERROR, target `handler:<컨트롤러.메서드>`, reason 예외 클래스 이름).
