# 14-2 불변 백업과 복구 훈련
⏱ 약 12분 · 고칠 파일 설정 3개(`infra/backup/policy-writer.json`·`infra/backup/backup.sh`·`infra/compose.a11.yml`) + 자바 1곳(`DaonOpsBackupController`) · 새 파일 3개(`backup-init.sh`·`policy-restorer.json`·`audit.py`) · 아키텍처 **A11** · 방어 스위치 없음(구조라 끌 수 없다)

백업을 「있는 것」에서 「지울 수 없고, 실제로 돌아가 본 것」으로 바꿉니다. 겹은 셋입니다: **다른 저장소**(backup-vault), **다른 계정**(올리기만 되는 backup-writer, 읽기만 되는 backup-restorer), **다른 망**(backup, 앱은 이 망에 없다). 거기에 **객체 잠금**(보존 기간 안에는 아무도 못 지움)을 더합니다.

> 안전 원칙: 재연 T36은 「앱 자격증명을 가진 공격자가 백업을 지우려 한다」를 랩 자신의 자격증명으로 흉내 냅니다. 악성 코드·파일 암호화는 없습니다. 지우는 것은 가짜 시드 DB의 덤프이고, 지우기 전에 사본을 `.daon/replay-tmp/`에 두었다가 끝에 되돌립니다.

## 따라 하기
1. **레드부터 봅니다.**
   ```bash
   make goto L=14-2
   make up STACK=spring
   make replay T=36          # 앱 계정으로 앱 버킷 backups/mysql/의 최신 덤프가 지워짐 [레드](사본으로 되돌림)
   make check L=14-2
   ```
2. **A11로 바꿉니다(✏️ `infra/compose.a11.yml`).** 정답 파일을 읽어 봅니다(`make solution L=14-2`).
   - `backup-vault`: 앱 MinIO와 다른 컨테이너·볼륨·루트 계정. `backup` 망(internal)에만 붙습니다. 감사 로그를 `backup-audit`로 보냅니다.
   - `backup-init`(한 번 돌고 끝남): 버킷 `daon-backup`을 **만들 때** 객체 잠금을 켭니다(나중에는 켤 수 없습니다). 기본 보존 랩 **COMPLIANCE 1일**(회사 예시 30일 이상), 수명 주기 규칙(보존이 끝난 뒤 정리). 계정 둘을 만들어 접속 정보를 전용 볼륨에만 둡니다. 백업 전용 DB 계정(`daon_backup`, mall 읽기만)도 만듭니다. 옛 백업(앱 버킷 `backups/`)은 잠금 버킷 `legacy/`로 옮긴 뒤 앱 버킷에서 지웁니다.
   - `backup-job`: 환경 변수에서 앱 계정(`MINIO_ACCESS_KEY`)을 지우고 backup-writer 볼륨을 붙입니다. 망은 `data`(DB)·`backup`(저장소).
3. **올리기만(✏️ `infra/backup/policy-writer.json`).** `s3:PutObject` 하나. `DeleteObject`·`PutBucketPolicy`·`PutObjectRetention`·`BypassGovernanceRetention`은 넣지 않습니다. 오래된 백업은 사람이나 앱이 아니라 수명 주기 규칙이 지웁니다.
4. **백업 한 번(✏️ `infra/backup/backup.sh`).** 덤프(백업 전용 읽기 계정) → 압축 → sha256 → 잠금 버킷. 해시와 덤프 시작 시각(복구 시점)을 메타데이터로 남깁니다. `set -euo pipefail`: 덤프가 실패하면 아무것도 올리지 않고 0이 아닌 값으로 끝납니다. 비밀번호·키는 명령 인자로 넘기지 않습니다.
5. **앱은 백업에 닿지 않는다(✏️ `DaonOpsBackupController`).** 앱 버킷 `backups/`를 읽던 코드를 지우고 410과 안내 문구만 줍니다. 백업 상태는 사람이 백업 계정으로 봅니다(`make backup-status`).
6. **확인합니다.**
   ```bash
   make up STACK=spring           # backup-vault·backup-init·backup-audit가 생기고 backup-job이 다시 뜸
   make logs S=backup-init        # 「[A11] 준비 끝」
   make backup-now                # 「잠금 버킷, backup-writer」
   make backup-status             # 보존 COMPLIANCE ~기한 · 복구 시점
   make replay T=36               # 앱 계정으로 backup-vault에 닿지 않음 · backup-writer로도 지우기 거부 [그린]
   make restore-drill             # 최신 백업 → 해시 확인 → mysql-restore에 복구 → 확인 시험 → RTO·RPO
   make check L=14-2              # 8개(정상 1개)
   make mem                       # backup-vault +128MB 근처
   ```
7. **숫자를 크게 적습니다.** `make restore-drill`의 `RTO 0분 00초 · RPO 00분`을 수업 노트에 옮깁니다. 「복구가 끝났다」는 데이터가 들어간 때가 아니라 확인 시험(주문 300건 이상·회원 40명 이상·alice 자기 주문)이 통과한 때입니다. 개인정보 칸은 암호문 그대로 돌아옵니다(키는 OpenBao에서 따로 복구, 5-3).
8. **탐지.** `make logs S=backup-audit | grep SECURITY` → `backup.denied.delete`(actor `minio:backup-writer`). Grafana에서는 `{app="backup-audit", stream="security"}`.

## 막힐 때
- 객체 잠금을 켤 수 없다: 버킷을 이미 잠금 없이 만들었습니다. `make wipe HARD=1`로 볼륨째 지웁니다(COMPLIANCE 잠금도 볼륨을 지우면 사라집니다. 랩만 그렇고, 회사 저장소는 그렇게 못 지웁니다).
- 랩 디스크가 찬다: 보존 기간을 짧게(`infra/.env`의 `DAON_BACKUP_RETENTION=1d`), 간격을 길게(`DAON_BACKUP_INTERVAL`) 둡니다.
- `make restore-drill`이 포트 충돌: 복구 컨테이너는 포트를 열지 않고 망도 없습니다. 이름이 겹치면 `docker rm -f daon-mysql-restore`.
- 「잠금이면 새 백업을 못 쓰게 하는 공격은?」: 잠금은 지우기만 막습니다. 마지막 백업이 기준(랩 15분)보다 오래되면 `backup.missed`가 울립니다.
- 「같은 PC인데 떨어진 곳인가?」: 아닙니다. 랩은 다른 컨테이너·다른 망으로 흉내 냅니다. 회사는 다른 계정·다른 매체·다른 장소에 사본을 하나 더 둡니다(3-2-1).
- Express: `diffs/s14-02/express.diff`는 같은 잠금 버킷에 PostgreSQL 덤프(`pg_dump`)를 올리는 작업을 더합니다.

## 확인 문제
1. 백업 작업 계정에 지우기 권한을 주지 않으면 오래된 백업은 어떻게 정리하나? (보존 기간이 끝나면 수명 주기 규칙이 지운다. 사람이나 앱이 지우지 않는다.)
2. 복구 훈련에서 「복구가 끝났다」의 기준은? (데이터가 들어간 것이 아니라 정해 둔 확인 시험이 통과한 시점.)
3. 앱 컨테이너를 `backup` 망에 붙이지 않는 이유는? (앱이 뚫려도 백업 저장소에 네트워크로 닿지 못하게. 자격증명 분리와 망 분리를 겹쳐 둔다.)

## 남는 이벤트
`backup.denied.delete`(WARN, 한 번이라도, backup-audit) · `backup.missed`(WARN, 기준 시간 초과, backup-audit) · `backup.restore.drill`(INFO, 도구 이벤트 `make restore-drill`).
