# 14-3 폭발 반경 줄이기와 축소 운영
⏱ 약 9분 · 고칠 파일 자바 4곳(고객 앱 `DaonPaymentGateway`·`DaonCheckoutController`, 관리자 앱 `DaonApprovedRefundPoller`·`DaonApprovalClient`) + 새 파일 5개(`DegradedMode`·`DaonPendingPayments`·`DaonModeController`·`DaonDegradedModeFilter`, 승인 서비스 `/breaker/hold`) + 설정 3개(`OpsElevationGate`·`MallSecurityConfig`·승인 서비스 `policy.yml`) · 아키텍처 변화 없음 · 방어 스위치 `degraded-mode`

결제사가 **오류 없이 느려지기만** 해도 서비스 전체가 멈출 수 있습니다. 느린 호출이 요청 처리 스레드를 오래 붙잡으면, 결제와 상관없는 상품 목록이 쓸 자리가 없어집니다. 9-5는 「오류 → 재시도 폭주」였고, 오늘은 「오류 없는 느림 → 자원 고갈」입니다. 칸막이(벌크헤드)로 자원을 나누고, 결제가 아픈 동안에는 그 기능만 끄는 **축소 운영**을 만듭니다: **주문은 받고 정산은 멈춘다.**

> 안전 원칙: 느린 결제사는 가짜 결제사 스텁의 느림 모드(3초, 오류 없음)로만 만듭니다. 동시 요청 수(40)·지연(3초)·기준 시간(1.5초)은 랩 값이고 바꿀 수 없습니다. 고객 앱의 요청 처리 스레드는 PC 한 대에서 보이도록 24개로 줄였습니다(회사 기본 200).

## 따라 하기
1. **레드부터 봅니다.**
   ```bash
   make goto L=14-3
   make up STACK=spring
   make replay R=14-3            # 결제 확인 40개 동시 → 상품 목록 3초 넘게 [레드]. 끝나면 스텁을 되돌린다
   make check L=14-3
   ```
   원인 화면: `make stub-fault S=pay MODE=slow MS=3000` 뒤 결제 확인을 여러 개 보내고 관리 포트에서 스레드를 봅니다(모두 결제사 응답을 기다림). 끝나면 `make stub-fault S=pay MODE=ok`.
2. **칸막이(✏️ 고객 앱 `DaonPaymentGateway.status()`).**
   - 결제사를 동시에 기다릴 수 있는 자리 6개(`Semaphore.tryAcquire()`, 대기 0). 자리가 없으면 바로 `PENDING_CHECK`(「결제 확인이 늦어지고 있습니다」).
   - 느린 호출 비율로 여는 서킷 브레이커(2초 넘는 호출이 최근 10번 중 절반 이상 → 20초 멈춤). 시간 제한 5초 → 2.5초.
   - 넘친 횟수는 `resilience.bulkhead.rejected`(INFO, 10초에 한 줄로 묶음).
3. **축소 운영 스위치(✏️ mall-security 새 파일 `DegradedMode`).** Redis `mall:mode:payment = normal | degraded`, 매 요청 읽습니다.
   - 고객 앱(✏️ `DaonCheckoutController`): 축소 운영이면 결제사를 부르지 않고 대기 큐 `daon.pay.pending`(새 파일 `DaonPendingPayments`)에 넣고 202 「결제 대기」. 끄면 1초에 3개씩 9-5 결제 요청 큐로 옮깁니다(한꺼번에 몰리지 않게).
   - 관리자 앱: 새 파일 `DaonDegradedModeFilter` → 반품 확인·환불 실행 503 + 안내 문구. ✏️ `DaonApprovedRefundPoller`는 지연 실행 환불을 가져가지 않습니다.
   - 승인 서비스: 새 `POST /breaker/hold` → 출금 서킷 브레이커를 사람이 엽니다(승인 토큰 자동 발급 멈춤). **멈추는 쪽은 누구나, 다시 닫기는 서로 다른 두 사람**(13-4 그대로).
4. **켜고 끄는 문(새 파일 `DaonModeController`, `POST /daon/mode/payment`).** 사유 필수. 고위험 기능이라 권한표(✏️ `MallSecurityConfig`)와 13-6 권한 상승(✏️ `OpsElevationGate`에 묶음 `incident-response`, 승인 서비스 `policy.yml`에도 같은 이름)을 거칩니다. 켤 때 `ops.mode.degraded`(WARN), 켜고 끈 사람·사유는 감사 로그 `ops.mode.set`.
5. **확인합니다.**
   ```bash
   make up STACK=spring
   make replay R=14-3            # 결제사가 느려도 상품 목록 1.5초 안 [그린]
   make check L=14-3             # 4개(정상 1개). 권한 상승 → 축소 운영 → 결제 대기·환불 503·브레이커 OPEN → 끄면 대기 결제 처리
   make approval-status          # 출금 서킷 브레이커 OPEN(사람이 멈춤: 축소 운영)
   ```
   RabbitMQ 관리 화면(관리자 입구 8443 `/rabbitmq/`)에서 `daon.pay.pending`에 쌓인 메시지를 봅니다.
6. **스위치.** `make switch K=degraded-mode V=off` → `make replay R=14-3` 레드 → `V=on`.

## 막힐 때
- 재연이 레드가 되지 않는다: 스텁이 느림 모드인지(`make stub-fault S=pay MODE=slow MS=3000`), 고객 앱 스레드가 24개인지(`infra/compose.a11.yml`의 `SERVER_TOMCAT_THREADS_MAX`).
- 축소 운영을 켰는데 반영이 안 된다: Redis 값(`mall:mode:payment`)을 매 요청 읽습니다. `make logs S=mall-admin | grep ops.mode`.
- 축소 운영을 끄자 결제가 한꺼번에 몰린다: 대기 큐는 1초에 3개씩만 옮깁니다(9-5 재시도 예산과 같은 생각).
- 브레이커가 닫히지 않는다: 의도입니다. 재무 담당·운영 책임 두 사람이 `POST /breaker/close`로 닫습니다(13-4). 랩에서는 `make approval-reset`.
- Express: `diffs/s14-03/express.diff`는 결제 호출의 동시 실행 상한(작은 세마포어)과, 축소 운영일 때 환불 라우트가 503을 주는 미들웨어를 더합니다.

## 확인 문제
1. 오류가 아닌 「느림」이 서비스 전체를 멈추는 이유는? (느린 호출이 요청 처리 스레드·DB 연결 같은 공유 자원을 오래 붙잡아 다른 기능이 쓸 자리가 없어진다.)
2. 축소 운영에서 환불을 막는 이유는? (상태를 확신할 수 없는 동안 돈이 나가는 쪽을 멈추는 것이 더 안전하다. 주문 접수는 나중에 맞출 수 있다.)
